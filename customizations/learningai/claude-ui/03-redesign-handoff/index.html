Inspected baseline

Stack

The site is hand-written static HTML with inline scripts and shared vanilla JS (theme.js, learning-api.js, course-state.js), with no framework and no build step. It is served by a small Node server (frontend-server.mjs) that maps bare paths into learning-ai-design-assets/ and proxies /api/*. The backend is a plain Node http server (coolify-backend/server.mjs) on Railway Postgres. Auth uses email and password with an HttpOnly 30-day session cookie plus a CSRF token. There is no live AI coach: the feedback and tutor endpoints only store rows. Tests are about 45 Node check scripts plus a backend test with a fake database. There is no CI.

Priority problems

  1. P0

    The deployed code lives only in an unpushed branch, and the working tree beside it has diverged

    Live = 3b252c2 on codex/v3-launch-ready-main. GitHub main stops at 24 Jul. The local tree has 29 modified and about 40 untracked files (a “cave journey” rework) that aren’t deployed. Any implementation must branch from 3b252c2, not from the working tree, or it will ship unreviewed work.

    Also: HANDOFF.md says a project-scoped Railway token was pasted into a chat session. If it hasn’t been revoked, revoke it.

  2. P0

    Save state isn’t truthful across routes

    Preview hides itself outside the catalogue. Completion is recorded locally before the server confirms. Expired sessions look signed in while work queues silently. The dashboard reads progress from localStorage. Students can’t tell what will survive a device change.

  3. P1

    A new student can’t see what the course is

    The entry is a yes/no prompt, and the outline is hidden until they finish Lesson 1, make an account and answer the questionnaire. There is no plain course promise or total effort, and no way to look before committing.

  4. P1

    Attempts aren’t preserved, and help isn’t separated from independent work

    The lesson player has no first-attempt record, no hint ladder, and no independent check that hides help. Answer keys are in the page. Checks never block, and the end screen shows a % score that mixes assisted and unassisted answers.

  5. P1

    Account recovery is broken by configuration

    Password reset email isn’t configured. A student who forgets a password, or whose session expires, has no self-service way back to their saved work.

  6. P2

    Progress graphics carry meaning by color and static labels

    Arc-colored dots are aria-hidden, the SVG labels don’t change with progress, and the count isn’t announced. The production dashboard title still reads “Stage 1 Navigation Proof”.

  7. P2

    Projects have no publish path or reasoning evidence

    States are local draft → queued, and nothing beyond that. Consent to the gallery isn’t a separate, reversible choice. There are no fields for reproducible summary, tools, cautions, or attribution.

  8. P2

    No help or FAQ, and a stale /v2/ app with analytics

    Students have nowhere to ask about verification, privacy, school rules, or how progress is saved. The leftover app is a privacy and confusion risk.

Recommendation: A, keeping C’s brand cues

  • It makes revision visible. A notebook entry can’t be silently overwritten, so “your first attempt survives revision” shows in the layout, not only in the code.
  • It reads well at every size. A single column survives 375px phones and 200% zoom with no layout change. B’s split panes turn into tabs on phones, which hides the sources while students write.
  • Fewer contrast problems. Text on blurred, translucent glass over a photo is the main contrast risk today. Flat paper removes it.
  • Continuity for the two testers. Keep the dark primary button, the brass accent for awards, and the paper photo on the entry screen only. Returning testers will still recognise the site.
  • B wins on desktop for long source packets. A borrows from it: at 1100px and wider, source cards dock into the margin.

Lesson layout by viewport

There is no permanent three-panel layout. The column is the default, and panels appear only when the screen is wide enough to show sources and writing side by side without squeezing either one.

Behaviour rules

  • Reload: restore the local draft first. Then compare it with the server copy by version; if they differ, show the two-versions state. Never silently replace the draft.
  • Back and outline: leaving a step saves the draft locally first. The outline link never discards work.
  • Log out: if anything is unsynced, the student sees “2 changes haven’t saved yet” with Save first / Download / Log out anyway. Local copies are then cleared, so the next person on a shared computer can’t see them.
  • Cross-device: only work that reached “Saved” appears on another device. The resume card says when it was last saved.
  • Lesson completion is recorded as done only after the server confirms it. Until then the dashboard says “Finished on this device, not yet saved”. This replaces today’s local-first complete().

Accessibility and privacy

  • Target: WCAG 2.2 AA. Test keyboard order, visible focus, a heading per step, labelled fields, 4.5:1 text contrast (measured on flat surfaces, no glass), reflow at 320px and 400% zoom, and 24px minimum targets (44px preferred).
  • Announcements: the save chip and feedback use role="status". Progress text updates with the same value as the graphic. The route-guard blank screen (visibility:hidden for up to 4s) is replaced by a visible “Checking your account…” message.
  • No colour-only state: every pill has a symbol and words. Selected options get a check mark and aria-pressed.
  • Motion: keep the existing reduced-motion handling. The reward medal’s infinite pulse stops under reduced motion.
  • No drag-only interactions. Sorting claims uses buttons.
  • Data minimisation: store attempts, hint levels opened, and criterion results. Don’t log keystrokes, timings per keypress, prompts sent elsewhere, or full sessions. Retire /v2/ and its Google Analytics tag.
  • Visibility: every saved response states who can see it.
